## 🆕 Фамильное древо (схема БД → v15)

### Что добавлено

- **Экран «Фамильное древо»** — `lib/screens/family_tree_screen.dart`.
  Узлы-родственники раскладываются по поколениям, связи рисуются линиями
  (`CustomPaint`), зум и перетаскивание — `InteractiveViewer`.
  Без сторонних пакетов: только Flutter SDK.
- **Таблица `relations`** в базе:
  `id, a_id, b_id, type`, где `type`:
  - `father` / `mother` — `a_id` родитель `b_id`;
  - `spouse` — `a_id` и `b_id` супруги.
  Внешние ключи с `ON DELETE CASCADE` — при удалении человека связи пропадают сами.
- **Указание связей в профиле** (`lib/screens/family_screen.dart`):
  в диалоге «Новый член семьи / Редактировать» появился блок
  **«Связи в древе»** — три выпадающих списка: **Отец**, **Мать**, **Супруг(а)**.
- **Возраст в дереве и профиле** — общий модуль `lib/utils/person_utils.dart`
  (даты в двух форматах, склонения «год/года/лет», ближайший ДР, разбор ФИО).
- **В профиле человека** теперь видно: «Отец: …», «Мать: …», «Супруг(а): …», «Дети: …».
- **Кнопка «Древо»** в шапке вкладки «Семья» (иконка `account_tree`).

### Как пользоваться

1. «Семья» → добавить людей (имя + дата рождения).
2. Открыть карточку → «Редактировать профиль» → заполнить блок «Связи в древе».
3. Нажать иконку дерева в шапке — древо построится автоматически.

### Защиты от ошибок

- **Циклы запрещены**: нельзя сделать отцом/матерью собственного потомка
  (проверка `_isDescendant` обходом в ширину) — иначе древо зациклилось бы.
- **Супруги на одном уровне**: если у супругов «разные» поколения, они
  выравниваются, а в ряду ставятся рядом (union-find по брачным связям).
- Если сохранённая связь указывает на удалённого человека, выбор в выпадающем
  списке сбрасывается — иначе `DropdownButtonFormField` падает на неизвестном значении.

### Миграция

Версия схемы: **15**. Изменение добавляет только новую таблицу `relations`
и индексы к ней. Существующие данные (дела, покупки, ДР, заметки, желания)
не затрагиваются — миграция выполняется автоматически при первом запуске.

## 🆕 Синхронизация между устройствами (схема БД → v16)

Один общий аккаунт семьи: вход по e-mail и паролю, на всех телефонах вводятся
те же данные, списки общие.

### Как устроено

- Приложение работает **офлайн**: локальная SQLite остаётся главным хранилищем.
  Сеть нужна только на время обмена.
- У каждой строки появились `sync_id` (UUID) и `updated_at` (мс epoch).
  Их заполняют **SQLite-триггеры**, поэтому существующий код сохранения
  менять не пришлось — время обновления проставляется автоматически.
- Удаления фиксируются в таблице `sync_tombstones`: без этого удалённая
  запись «воскресала» бы при следующем обмене.
- Обмен: сначала забираем облако, затем отправляем свои изменения.
  Конфликты решаются по принципу «побеждает более поздняя правка»
  (last-write-wins по строке).
- Внешние ключи (`birthday_id`, `task_id`, `a_id`/`b_id` у связей древа)
  между устройствами передаются как `sync_id`, потому что локальные
  `INTEGER id` на разных телефонах разные.

### Безопасность

- В облаке одна таблица `family_data` с политиками RLS по `owner = auth.uid()`:
  даже с anon-ключом из APK чужие данные прочитать нельзя.
- `anon`-ключ передаётся при сборке и в репозитории не хранится.
  `service_role`-ключ приложению не нужен и нигде не используется.
- Если ключи при сборке не переданы — приложение работает локально,
  а экран синхронизации сообщает, что она не настроена.

### Почему без `supabase_flutter`

Первая попытка использовала пакет `supabase_flutter`, но сборка упала
на нативном плагине `app_links` (транзитивная зависимость):

```
Could not get unknown property 'flutter' for extension 'android'
Build file '.../app_links-6.4.1/android/build.gradle' line: 28
```

Это несовместимость `app_links` с Flutter 3.24 / AGP 8.3, к нашему коду
отношения не имеет. Вместо подбора версий плагина синхронизация переписана
на **чистый HTTP** через пакет `http`:

- вход/регистрация — `POST {url}/auth/v1/token?grant_type=password`
  и `POST {url}/auth/v1/signup`;
- чтение — `GET {url}/rest/v1/family_data?select=*`;
- запись — `POST {url}/rest/v1/family_data?on_conflict=sync_id`
  с заголовком `Prefer: resolution=merge-duplicates`;
- токены (access + refresh, срок жизни) хранятся в `shared_preferences`,
  токен продлевается автоматически.

Итог: в проекте больше нет ни одного нативного плагина ради синхронизации,
и проблема Gradle исчезла вместе с ним.

### Исправления по результатам следующих сборок

**1. `flutter analyze` падал на чужом тесте.**
`flutter create` в CI генерирует `test/widget_test.dart`, который ссылается
на несуществующий `MyApp` → ошибка `The name 'MyApp' isn't a class`.
Теперь в репозитории лежит собственный `test/widget_test.dart` с тестами
чистых функций (`parseFlexibleDate`, `pluralize`, `ageText`, `splitFullName`) —
`flutter create` не перезаписывает существующие файлы.

Заодно шаг `Analyze` в CI стал **блокирующим** (раньше был `continue-on-error`):
теперь ошибки компиляции видны точным сообщением `файл:строка: Error: …`,
а не тонут в логах Gradle.

**2. `lintVitalAnalyzeRelease` падал на D8 при десугаринге.**

```
Execution failed for task ':app:lintVitalAnalyzeRelease'.
> Failed to transform FakeDependency.jar ...
  > D8BackportedMethodsGenerator ... Cannot invoke "JT.warning(...)" because "this.d" is null
```

Причина: AGP 8.1 из шаблона Flutter 3.24 не умеет десугарить
`desugar_jdk_libs 2.0.4`. Исправлено в воркфлоу:

  (AGP 8.3 требует Gradle 8.4+), Kotlin остаётся 1.9.24;
- в `android/app/build.gradle` добавляется `lint { checkReleaseBuilds false }`
  — задача `lintVital` для release больше не запускается (сам анализ кода
  выполняет `flutter analyze`).

## Исправления по результатам первой сборки CI

Сборка `Build APK` выявила 4 ошибки компиляции — все устранены:

### 1. `lib/screens/add_edit_screen.dart` — `'Database' isn't a type`

В сигнатурах `_savePurchase(Database db, ...)` и `_saveTask(Database db, ...)`
использовался тип `Database` из пакета `sqflite`, но импорт отсутствовал.
Добавлено:

```dart
import 'package:sqflite/sqflite.dart';
```

### 2. `lib/screens/family_screen.dart` — `The argument type 'String?' can't be assigned to 'String'`

В диалоге добавления/редактирования члена семьи переменная `photoPath`
объявляется как `String?` и **перезаписывается** внутри замыкания
`setDialogState(() => photoPath = picked.path)`. Из-за этого Dart не «повышает»
её тип до `String` (type promotion не работает для переменных, изменяемых
в замыканиях), и `File(photoPath)` не компилировался.

Исправлено добавлением `!` в двух местах диалога:

```dart
if (photoPath != null && File(photoPath!).existsSync())
...
backgroundImage: FileImage(File(photoPath!)),
```

Аналогичные места, где переменная объявлена как `final`
(`_showProfile`, `_buildMemberCard`), менять не потребовалось —
для `final`-переменных promotion работает и внутри замыканий.

> Полезное правило на будущее: если nullable-переменная изменяется внутри
> замыкания (`setState`/`setDialogState`), Dart не повышает её тип до
> не-null — нужен `!` или отдельная локальная `final`-копия.

### 3. `lib/utils/notification_service.dart` — обязательный параметр `zonedSchedule`

```
Error: Required named parameter 'uiLocalNotificationDateInterpretation' must be provided.
```

В `flutter_local_notifications` **17.2.2** параметр
`uiLocalNotificationDateInterpretation` не удалён, а **обязателен**.
